# X301: internal v2 raw XDH contract

Phase-B reference specification, awaiting Claude's Gate B. Not standardized,
not production-ready, and not a constant-time implementation certification.

## Authority and standards boundary

Martin's decision is revision 2 of
`phase-b/inputs/X301-v2_EINGABEVERTRAG_2026-09-10.md`, SHA-256
`b33d3fe0bf6b5b026192695902902f4b7592d4271ca98161f47920b47c6a1c2c`.
The copy is unchanged. Its document date is 2026-09-10.

The agreed formulation is:

> X301-v2 übernimmt die strikten Kodierungsregeln nach dem Vorbild von RFC 8032
> und verwendet eine Montgomery-Leiter nach dem Konstruktionsmuster von RFC 7748.

This borrows the canonical-decoding principle from
[RFC 8032 section 5.2.3](https://www.rfc-editor.org/rfc/rfc8032.html#section-5.2.3).
RFC 8032 specifies signatures, not this DH function. X301 deliberately does
not adopt the noncanonical-input acceptance required for X25519/X448 by
[RFC 7748 section 5](https://www.rfc-editor.org/rfc/rfc7748.html#section-5).
This is contract clarity, not a claimed cryptographic advantage over X448.

Consequences: X301 is not a drop-in for X448 expectations; each field value
has one accepted u encoding. This excludes encoding aliases, not DH/TLS
malleability generally or equal DH outputs from distinct field values.
Early rejection depends only on public input and reveals no secret scalar;
it does not replace constant-time validation of the secret computation.
Only secret clamping changes input bytes, on a copy. Raw secret bytes are
not canonical field/scalar encodings and are exempt from the u-decoder rule.

## Parameters and API

All field, curve, order and basepoint values come from the immutable Gate-A
file `provenance/phase-a/2026-09-09/parameter/ed301-v2.json`, SHA-256
`13f0eaf541919a1447b9d3c58e6d57eb77ffab94ebe37539c70301d6fddcfaa0`.
Use its Montgomery model `B*v² = u³ + A*u² + u` and basepoint's u encoding.

The Python reference provides `x301(secret, u_encoding)`,
`public_from_secret(secret)`, `shared_secret(secret, peer_public)`,
`import_secret(secret)` and `keygen(random_bytes=os.urandom)`.
Inputs and successful outputs are bytes. Public and shared values are
exactly 38 bytes. Secret import validates but preserves the original raw
38 bytes. No KDF, format guessing, alternate-curve fallback, authentication
or public-key ownership check is implied by successful raw DH.

## Strict peer decoding

Before any ladder step, require a byte string of exactly 38 bytes. Require
`encoded[37] & 0xe0 == 0`; decode the little-endian integer and require
`0 <= u < p`. Never mask, reduce or otherwise normalize peer bytes.
This includes rejection of the raw integer encodings of p, p+1, p+2 and
2^301-1, even though their reductions would be field elements.
`FE(p)` is not a valid field encoding: negative vectors use raw integer
serialization explicitly, not the canonical FE encoder.

## Secret clamping and excluded twist order

Require exactly 38 raw secret bytes, make a copy and apply
`k[0] &= 0xfc; k[37] = (k[37] & 0x0f) | 0x10`.
The integer is `2^300 + 4*n`, with `0 <= n < 2^298`.
Compare the entire clamped 38-byte string with the Gate-A twist order's
little-endian encoding, and reject equality:

```text
N_t = 4074071952668972172536891376818756322102936786019054572921615708584947563249005641551956612
N_t_le = 84ca911e62530d13b204a5718d1a9ada9621c5ffffffffffffffffffffffffffffffffffff1f
```

N_t itself is in the clamp interval, is divisible by four, and remains
unchanged by clamping. This value annihilates every twist point. There are
64 raw input aliases for each clamped value: two low input bits and four
bits of the last byte are overwritten. Exactly one of 2^298 clamped values
is excluded, giving rejection probability 2^-298 for uniform raw secrets.

Import, Public and Shared MUST reject all 64 aliases. KeyGen MUST resample
only this error with fresh system-CSPRNG bytes; RNG failures, wrong types or
lengths, and internal arithmetic failures are errors, not retry conditions.
A hardened implementation MUST compare the fixed-length secret bytes in
constant time. The references use `hmac.compare_digest` and
`crypto.timingSafeEqual`; this does not make their surrounding arithmetic
constant-time or prove compiler/platform behavior for later implementations.

Since q and q_t are odd, a clamped multiple of either subgroup order must be
a multiple of four times that order. `4q >= 2^301` excludes main-group
annihilators. For the twist, the only such value inside the clamp interval
is N_t; the next multiple is outside it. The reference tests recalculate
these bounds for v2 instead of copying v1 congruences.

## Ladder and mandatory result checks

Run exactly 301 bit iterations from bit 300 through bit 0. Leading zero
bits are included by the underlying mathematical ladder. Use the Gate-A
`A24_minus = (A-2)/4 mod p` with `Z2 = E*(AA + A24_minus*E)`.
Do not substitute `(A+2)/4` in that formula. The x-only function processes
curve and twist inputs identically, without point recovery or classification.

A hardened implementation MUST make the ladder constant-time with respect
to the secret. The Phase-B Python and Node references intentionally do not
meet or claim that implementation gate.

Infinity (`Z = 0`) is an error. Otherwise recover the affine u value and
encode it canonically in 38 little-endian bytes, with bits 301..303 zero.
An all-zero encoded result is also an unconditional error, without partial
or substitute output. A hardened implementation MUST perform the result
check without a data-dependent early byte exit. The libraries used by these
references supply the fixed-length byte comparison.

This mandatory all-zero policy mirrors the requirement for X25519/X448 in
[TLS 1.3 section 7.4.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-7.4.2),
whereas RFC 7748 describes an optional check. X301 requires it even outside
TLS. Neither reference's raw output should be used directly as a symmetric
key: the surrounding protocol must provide its own reviewed KDF and binding.

## Error and vector contract

Malformed input raises ValueError (RangeError in Node) before ladder entry.
The excluded secret raises the more specific WeakSecretError. Infinity or
an all-zero result raises AllZeroError. No failure returns output bytes.
Only KeyGen retries WeakSecretError; all other errors propagate.

`vectors/x301-v2.json` contains 7 keys, 4 two-way DH pairs, 24 curve/twist
evaluations, 33 malformed/all-zero cases and 64 excluded raw secrets. Types
that JSON cannot represent as byte strings are covered by API tests.
The finite canonical small-order u values are 0, 1 and p-1: the Gate-A
non-square A²-4 leaves only u=0 at order two, and the doubling numerator
`(u²-1)²` gives the order-four preimages. These are not decoder failures;
their ladder result fails. Infinity has no accepted affine wire encoding.

The RFC-7748-style iteration test starts `k_0 = u_0 = BASE_U_ENCODING`,
then sets `(k_i,u_i) = (X301(k_(i-1),u_(i-1)), k_(i-1))`.
The corpus fixes checkpoints 1, 10, 100 and 1000. This newly generated
chain does not inherit v1 expected bytes or claim a million-iteration run.

The integration baseline's masking/reduction acceptance tests are historical,
not normative v2 tests; see `phase-b/HISTORICAL_X301_TESTS.md`.
OID assignments, TLS codepoints and Raw-TLS versus Hybrid-only remain Phase D.
The integration baseline remains the source for future hybrid/provider/TLS
work with its decoder changed to this contract; no TLS result is claimed here.
